# Weeks 1–8 — Foundations, Retrieval, Evaluation, Agents

Session-by-session detail. Each week: **10 one-hour blocks** (Mon AM through Fri PM), a named deliverable, and five oral-exam questions for the Friday gate.

Wednesday PM rotates the **designated tool** so you build fluency across your whole harness by doing real work in each.

A note on sources: where I name a specific paper or doc, read the primary source, not a summary of it. The summary is what everyone else has read, and the difference between you and them in an interview is that you read the actual thing.

# WEEK 1 — LLM mechanics from first principles
**Aug 26–28 (Wed start — 6 blocks)** · Designated tool: Claude Code

You have 25 years of systems intuition and no mechanical model of how a transformer produces a token. That gap is the reason GenAI feels like magic rather than engineering, and it's why interview answers come out hedged. This week closes it. By Friday you should be able to explain, at a whiteboard, everything that happens between an HTTP request and a streamed token — and you should never again be surprised by an LLM failure mode, because you'll know where they come from.

| Block | Work |
|---|---|
| **Wed AM** | Tokenization. Read Karpathy's `minbpe` README and walk the BPE algorithm. Tokenize text in several languages plus numbers and code; observe the cost asymmetry. Teach-back: *why tokenization causes arithmetic, spelling, and non-English cost failures.* |
| **Wed PM** | Build the bare inference harness. Direct `boto3` `bedrock-runtime` Converse calls — no LangChain, no wrappers. Print input tokens, output tokens, stop reason, latency. This harness is reused all program. |
| **Thu AM** | The forward pass, then sampling. Jay Alammar's *Illustrated Transformer* + 3Blue1Brown's attention chapter; then temperature, top-p, top-k, min-p, logprobs, and why `temperature=0` is not a determinism guarantee in a distributed serving stack. Teach-back: *what lives in the KV cache, and why prefill and decode have different performance characteristics.* |
| **Thu PM** | Add streaming to the harness. Measure time-to-first-token separately from tokens-per-second and explain the gap in terms of prefill vs decode. Then a short sampling sweep — 3 prompts x 3 runs at two temperatures — and record the output variance you observe. |
| **Fri AM** | **Frontier watch #1 — landscape baseline.** Establish, yourself, from primary sources: current flagship models per provider, which are on Bedrock, which are not. Write `LANDSCAPE.md`. Do not trust any list I or anyone else gives you; this field moves too fast for secondhand inventories. |
| **Fri PM** | **GATE 1.** |

**Deliverable:** `week01/` — inference harness with streaming and token accounting, a recorded sampling-variance observation, `LANDSCAPE.md`, two teach-back notes.

*Six blocks, not eight: Day 1 slipped to Wednesday Aug 26 while the delivery pipeline was repaired. Build scope was cut to fit. The gate and all five oral questions below were not — that is the rule in `00-PROGRAM.md`: when you're short, cut build scope, never the gate.*

**Oral exam:**
1. Mechanically, why does an LLM miscount the letters in a word?
2. What's stored in the KV cache, and why does prompt caching reliably cut cost but only sometimes cut latency?
3. Temperature is zero. Is the output deterministic? Defend your answer.
4. Walk me through everything between my HTTP request and the first streamed token.
5. Why is a 200K context window not 200K of *usable* context?

# WEEK 2 — Inference control & the API as an engineering surface
**Aug 31–Sep 4** · Designated tool: Claude Code

Most people treat the model API as a text box. It's a control surface with maybe fifteen meaningful knobs, and knowing them is the difference between "the model is unreliable" and "I configured it wrong." This week is also where you first confront cost as a first-class design constraint, which is a conversation you'll have with every customer you ever advise.

| Block | Work |
|---|---|
| **Mon AM** | Read the Bedrock Converse API reference and the Anthropic Messages API reference *side by side*. Note where the abstraction leaks. Teach-back: the full parameter surface and what each controls. |
| **Mon PM** | Structured output, three ways: prompted JSON, forced tool-call schema, and native structured-output/response-format. Run each 50 times on the same input. Record parse-failure rates. |
| **Tue AM** | Tool-calling mechanics. What the model actually emits, who executes it, the caller's loop, parallel tool calls, and `tool_choice` semantics. |
| **Tue PM** | Hand-roll a complete tool-calling loop against your harness. No framework. This is the direct foundation for Week 7 — do it properly. |
| **Wed AM** | Reasoning and extended thinking. Thinking budgets, interleaved thinking, when reasoning models help and the documented cases where they hurt. Cost implications of thinking tokens. |
| **Wed PM** | Build the **prompt regression harness**: fixed test cases, run across models and settings, diff outputs, track cost per run. This becomes infrastructure for the rest of the program. |
| **Thu AM** | Prompt caching, batch inference, and the cost/latency arithmetic. Cache breakpoints, TTL, what invalidates a cache, and how caching should reshape prompt *architecture*. |
| **Thu PM** | Add cost accounting and cache-hit reporting to the harness. Every call should report what it cost. |
| **Fri AM** | Frontier watch. |
| **Fri PM** | **GATE 2.** |

**Deliverable:** `week02/` — prompt regression harness with cost accounting, structured-output failure-rate comparison, hand-rolled tool loop.

**Oral exam:**
1. Three ways to get valid JSON out of a model. Rank them and give each one's failure mode.
2. What exactly does the model emit for a tool call, and whose responsibility is execution?
3. Name a case where extended thinking makes output *worse*.
4. How should prompt caching change the way you structure a prompt?
5. 50K-token system prompt, 200 calls/day. Cost with and without caching — show the math.

# WEEK 3 — Context engineering
**Sep 7–11 (Labor Day Monday — 8 blocks)** · Designated tool: Codex

This is the week JHU doesn't have, and it's arguably the most important week in the program. "Prompt engineering" as a discipline largely dissolved into context engineering during 2025: the job is no longer writing clever instructions, it's deciding what occupies a finite, degrading, expensive context window at each step. This is a resource-allocation and systems problem, which means your background gives you an actual edge here. Lean in.

| Block | Work |
|---|---|
| **Tue AM** | Read Anthropic's *Effective context engineering for AI agents* and Cognition's *Don't Build Multi-Agents* back to back. They disagree productively. Teach-back: context as a budgeted, degrading resource. |
| **Tue PM** | Build a **context budget analyzer**: for a given task, break down token allocation across system prompt, tool definitions, conversation history, retrieved content, and output reserve. Visualize it. |
| **Wed AM** | Long-context failure modes. Read *Lost in the Middle* (Liu et al.). Understand positional attention bias, distractor sensitivity, and what practitioners now call context rot. |
| **Wed PM** | Run your own needle-in-a-haystack experiment with distractors, varying needle position and haystack depth. Chart retrieval accuracy by position. Do not skip this — measuring it yourself is what makes you believe it. |
| **Thu AM** | Memory and compaction. Summarization strategies, structured note-taking, external memory stores, and sub-agent context isolation as a context-management technique. |
| **Thu PM** | Add compaction to your harness. Measure quality loss against tokens saved. Find the knee in the curve. |
| **Fri AM** | Frontier watch. |
| **Fri PM** | **GATE 3.** |

**Deliverable:** `week03/` — context budget analyzer, position-bias chart from your own experiment, compaction implementation with a measured quality/cost curve.

**Oral exam:**
1. Distinguish context engineering from prompt engineering. Why did the emphasis shift?
2. 200K context, 900K-token corpus. Give me your options ranked by cost and quality.
3. What is context rot and how would you detect it in a production system?
4. Why does giving a sub-agent its own context window help? What problem is that solving?
5. Compaction destroys information. How do you decide what's safe to lose?

# WEEK 4 — Retrieval I: embeddings, chunking, vector search
**Sep 14–18** · Designated tool: Kiro

RAG is the most-demoed and least-well-built pattern in the industry. Nearly every failure is a retrieval failure, not a generation failure, and nearly every team debugging "the LLM is wrong" is actually looking at bad chunks. You'll build it from bare numpy up to a managed Bedrock Knowledge Base so you know exactly what the managed service is doing for you and what it's hiding.

| Block | Work |
|---|---|
| **Mon AM** | Embeddings from first principles, then read the original RAG paper (Lewis et al., 2020). Teach-back: what a cosine similarity score does and does not tell you. |
| **Mon PM** | Manual retrieval: embed a corpus, store vectors in numpy, implement cosine search yourself. No vector database. Feel the mechanics bare. |
| **Tue AM** | Chunking strategies: fixed-size, recursive, semantic, hierarchical/parent-document, and late chunking. Trade-offs and when each wins. |
| **Tue PM** | Same corpus, four chunking strategies, one question set. Compare retrieval hit rates. Write down which won and your hypothesis for why. |
| **Wed AM** | Vector indexes and the AWS storage menu. HNSW vs IVF, the recall/latency/cost triangle. Survey and verify current options: OpenSearch Serverless, S3 Vectors, Aurora pgvector, Bedrock Knowledge Bases. |
| **Wed PM** | Stand up a Bedrock Knowledge Base end to end on the Project 1 corpus. |
| **Thu AM** | Hybrid search and reranking. BM25 plus dense, reciprocal rank fusion, cross-encoder rerankers, and why hybrid so often beats either alone. |
| **Thu PM** | Add hybrid retrieval and a reranker. Measure the delta against your Wednesday baseline. Report cost and latency impact alongside quality. |
| **Fri AM** | Frontier watch. |
| **Fri PM** | **GATE 4.** |

**Deliverable:** `week04/` — bare-numpy retriever, four-way chunking comparison with numbers, working Bedrock Knowledge Base, hybrid+rerank with a measured delta.

**Oral exam:**
1. Two documents score 0.87 cosine similarity. What does that actually tell you?
2. Pick a chunking strategy for dense technical PDFs with tables. Defend it.
3. HNSW vs IVF — when does each win, and what do you trade?
4. Why does hybrid search usually beat pure dense retrieval?
5. What is Bedrock Knowledge Bases doing for you, and what is it hiding that you'd need to control at scale?

# WEEK 5 — Retrieval II + **PROJECT 1**
**Sep 21–25** · Designated tool: Cowork

This week you go from "a RAG system" to "a RAG system with evidence." The evaluation harness is the deliverable that matters. Anyone can wire a vector store to a model; almost nobody can tell you their retrieval recall or what their system gets wrong. Being the person who can is most of the credibility gap you're trying to close.

| Block | Work |
|---|---|

| **Mon PM** | Build a golden question set for Project 1 — minimum 30 questions with known-correct source passages. Tedious, unglamorous, and the single highest-leverage artifact you'll build this month. |
| **Tue AM** | Advanced RAG patterns: query rewriting, HyDE, multi-query fanout, self-query filtering, Self-RAG, Corrective RAG. |
| **Tue PM** | Implement query rewriting and multi-query into Project 1. Measure against your golden set. |
| **Wed AM** | GraphRAG and structured retrieval. Entity graphs, community summarization, when a graph genuinely beats vectors, and text-to-SQL as a retrieval strategy. |
| **Wed PM** | Project 1 assembly — full pipeline wired together, driven from Cowork. |
| **Thu AM** | Agentic RAG: retrieval as a tool the model chooses to invoke, iterative and self-correcting retrieval loops. |
| **Thu PM** | Project 1 hardening: cost per query, p50/p99 latency, and a written, honest inventory of what it gets wrong. |
| **Fri AM** | Frontier watch. |
| **Fri PM** | **GATE 5 = PROJECT 1 defense.** |

**Deliverable:** **Project 1 — Architecture Standards Advisor.** Retrieval over AWS Well-Architected content plus a synthetic internal-standards corpus. Must include: measured retrieval quality against the golden set, a documented and defended chunking decision, cost per query, latency distribution, and a written failure inventory.

**Oral exam:**

2. When does GraphRAG justify its considerable extra complexity?
3. Difference between agentic RAG and a retrieval step in a fixed pipeline — and what does that cost you?

# WEEK 6 — Evaluation as an engineering discipline
**Sep 28–Oct 2** · Designated tool: Claude Code

I moved evaluation to Week 6; JHU teaches it in Week 14. That's the most consequential structural change I made, and here's the reasoning: evals are the instrument that makes every subsequent week measurable. Learn them late and Weeks 7–13 are built on vibes. Learn them now and every agent you build afterward comes with evidence attached. This is also the skill most correlated with senior GenAI roles, because it's the one that requires engineering discipline rather than API familiarity.

| Block | Work |
|---|---|
| **Mon AM** | Read Hamel Husain's writing on evals and error analysis, plus the evaluation chapters of Chip Huyen's *AI Engineering*. Teach-back: why eval-driven development beats prompt-tweaking. |
| **Mon PM** | **Error analysis on Project 1.** Read 50 actual failures. Hand-label and categorize them into failure taxonomies. This is plausibly the single highest-value hour in the entire 16 weeks. |
| **Tue AM** | LLM-as-judge: position bias, verbosity bias, self-preference bias, and the calibration problem. |
| **Tue PM** | Build an LLM judge and calibrate it against your 50 hand-labels. Compute agreement — Cohen's kappa. If kappa is poor, your judge is decoration. |
| **Wed AM** | Eval design: golden sets, rubric construction, pairwise vs pointwise, sample size and statistical significance. How many examples do you actually need to detect a 5% regression? |
| **Wed PM** | Build a CI-runnable eval suite that fails the build on regression. |
| **Thu AM** | Tooling survey: Ragas, DeepEval, promptfoo, Langfuse, Braintrust, Bedrock model and RAG evaluation. Pick your stack and write down why. |
| **Thu PM** | Wire the eval suite into CI. Make a regression actually block a merge. |
| **Fri AM** | Frontier watch. |
| **Fri PM** | **GATE 6.** |

**Deliverable:** `week06/` — labeled failure taxonomy from 50 real errors, calibrated LLM judge with a reported kappa, CI-integrated eval suite that blocks regressions.

**Oral exam:**
1. Your LLM judge agrees with human labels 80% of the time. Usable? What's the kappa, and why does that matter more than the raw percentage?
2. How many eval examples to reliably detect a 5% quality regression? Reason it through.
3. Name three biases in LLM-as-judge and a mitigation for each.
4. Offline evals are green, production is degrading. What are your hypotheses?
5. How do you evaluate a task with no single correct answer?

# WEEK 7 — The agent loop from scratch + MCP
**Oct 5–9** · Designated tool: Codex

Now the core of the program. You will build an agent with no framework, because frameworks hide exactly the mechanics you need to be able to reason about under interview pressure. Then you'll build your own MCP server, because MCP is now the integration substrate for the entire ecosystem and the difference between consuming it and authoring it is large.

| Block | Work |
|---|---|
| **Mon AM** | Read the ReAct paper (Yao et al., 2022). Then confront the definitional question honestly: what distinguishes an agent from a workflow, and why does the distinction matter architecturally? |
| **Mon PM** | Build the agent loop from scratch. Perceive → decide → act → observe, real tools, real termination conditions. No framework, no exceptions. |
| **Tue AM** | Tool design as API design. Naming, descriptions as prompts, schema design, error messages the model has to read, and the token economics of tool results. |
| **Tue PM** | Build five well-designed tools. Then deliberately break one — bad description, misleading schema — and observe precisely how the agent's behavior degrades. |
| **Wed AM** | MCP deep dive. Read the spec: tools vs resources vs prompts, transports (stdio and streamable HTTP), the authorization model, elicitation, and sampling. |
| **Wed PM** | Build **your own MCP server** and connect it to Claude Code. You now understand the protocol from the server side, which most people never do. |
| **Thu AM** | Agent failure modes: infinite loops, tool thrashing, premature completion, context exhaustion, error cascades, and confidently wrong terminal states. |
| **Thu PM** | Harden: step limits, token budget caps, loop detection, structured error handling, and a kill switch. Your reliability instincts apply directly here. |
| **Fri AM** | Frontier watch. |
| **Fri PM** | **GATE 7.** |

**Deliverable:** `week07/` — framework-free agent with guardrails, five tools plus a documented tool-degradation experiment, a working MCP server connected to Claude Code.

**Oral exam:**
1. Agent vs workflow. Where's the line, and why does it change your architecture?
2. Why is a tool description a prompt? What happens when it's wrong?
3. Compare MCP transports. When would you choose each?
4. What does MCP give you that a well-documented internal function registry doesn't?
5. An agent is looping in production, burning $40/min. Walk me through detection and mitigation.
